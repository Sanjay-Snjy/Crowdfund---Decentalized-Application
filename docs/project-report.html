Project - Detailed Documentation

CrowdFund DApp — a crowdfunding app where the donors release the money

This is a crowdfunding website built on a blockchain. People donate ETH to a project. The money is not kept by the website or by any company — it is kept inside a smart contract. The creator gets the money in three steps (30%, 30%, then 40%). Before each step the creator has to show proof of work, and the people who donated have to vote yes. If the project does not reach its target, every donor can take their money back. Creating a campaign costs nothing.

1The project and the idea behind it

What it is

  • A crowdfunding site. People put money into a project they like.
  • The money is held by a smart contract, not by a bank account and not by the website owner.
  • The creator is paid in three steps: 30%, 30%, then 40%.
  • Before each step, the creator posts proof of work (a file), and the donors vote. Only after a "yes" vote does that part of the money move.
  • Creating a campaign is free. No deposit, no platform fee.
  • Every move of money is signed in the user's own wallet and can be checked on a block explorer by anybody.
  • If the target is not reached by the deadline, every donor can refund in full.

Problems with normal crowdfunding

  • The platform holds the money and decides when to pay it out.
  • All-or-nothing: the creator often receives 100% up front and may never finish the work.
  • Backers have no way to check the accounts themselves.
  • If a project quietly dies after funding, nobody is answerable.

How this project answers those problems

ProblemAnswer in this project
The platform controls the moneyEscrow inside the contract. The contract holds the donations. The owner cannot move donor money into their own wallet.
All the money is paid up frontMilestone release. 30 / 30 / 40. Later parts stay locked until earlier work is approved.
No proof of workEvidence on IPFS. For each milestone the creator posts a file plus a note, and the file's address is written on-chain with a timestamp.
Backers have no sayDonor voting. One ETH of donation = one unit of voting power. Approval needs a strict majority of the votes cast, and at least 50% of the power must take part.
A deposit would keep new creators outFree to launch. Accountability comes from the escrow, not from money paid up front.
No way to check the historyPublic events. Every action writes an event on-chain, so the whole history can be read on Etherscan.

The four roles in the system

RoleWhat they can doWhat they cannot do
Creator Create a campaign for free; post milestone proof; receive each approved part of the money Donate to their own campaign, vote, or take money out without donor approval
Donor Donate ETH; vote on each milestone with power equal to their donation; refund if the target was missed Vote twice, vote without donating, or vote before the proof is posted
Anyone Press the "release" button once a milestone is approved; read all data for free Change the outcome — they can only finish what the rules already allow
Owner (admin) Pause the contract, take the platform treasury, switch campaigns on or off, run an emergency withdrawal Release a milestone without donor votes, or take donor escrow as a normal fee

Who is allowed to move money

Pages decide what you see, and they show the "connect your wallet" message. Components draw the screen and collect what you type. hooks/useContract.js is the only place that talks to the blockchain. The contract is the only thing that can move money. Nothing else is trusted with it.

The main design rule

5Login and identity

The project has two different identities, and this is the key to understanding the login flow.

Identity A — the person (Clerk)

  • Email or Google sign-in through Clerk's window.
  • Gives a display name, a picture and an email address.
  • Fully optional: it only exists if a real Clerk key is set.
  • It is only for show and credit — no page is locked behind it.

Identity B — the wallet (MetaMask)

  • This is the identity that actually signs transactions.
  • It owns the money, the votes and the refunds.
  • Needed for every action that changes something: create, donate, vote, release, refund.
  • Just reading the site works with no wallet at all.
Important: login does not protect anything

There is no middleware.js in the project, so Clerk does not protect any page on the server. Any page can be opened directly. Pages that need money actions simply show a "Connect your wallet" card and the buttons stay disabled. So the real guard is the blockchain and the user's own wallet, not the login screen.

Two different meanings of "admin"

The header decides whether to show the Admin link by comparing the connected wallet with the NEXT_PUBLIC_ADMIN_ADDRESS setting. But the /admin page asks the contract who the owner is (owner()) and sends everyone else to the dashboard. The contract is the one that matters; the setting only decides whether the link appears.

Known gap — wallet linking is half-built

Only the lookup part of /api/wallet-link is used by the app. Nothing in the app ever sends the init / verify requests, so the profile list stays empty and creator names fall back to the name stored in the campaign metadata, or to a short address like 0x4bbB…44cA. The list is also kept only in the server's memory, so it is lost when the server restarts. The fix is a small database plus a "link wallet" screen.

6The main pages — /home, /dashboard, /create-campaign

These three pages carry most of the app. Here is what each one does.

/home — browse campaigns

What is on the page

  • A headline area with the numbers and recent activity running across the screen.
  • A "Trending Now" row of cards, with left / right arrows to scroll it.
  • "Explore by Category" tiles. Clicking a tile scrolls down to the results.
  • A search box, a status filter (All / Active / Funded) and a sort menu (Newest, Ending Soon, Most Funded, Most Popular).
  • A grid / list switch for the results, plus a count of how many campaigns were found.
  • If nothing matches, a "No campaigns found" message; if there are no campaigns at all, a friendly block with a link to create one.

Where the data comes from

  • The list of campaigns comes from the contract, through the wagmi hook layer.
  • Each card's title, description and image come from IPFS, looked up by the file address stored on-chain.
  • Filtering, searching and sorting happen in the browser after the data is loaded.
  • Bookmarks are saved in the browser's local storage, so they survive a refresh.
  • A small price call to CoinGecko turns ETH amounts into USD / INR for display.
Scalability note

The page asks the contract for every campaign, and the headline numbers need one network call per campaign. That is fine for a few dozen campaigns, but at a few thousand it would need an indexer or paging with totals worked out on the server.

/dashboard — the personal overview

What is on the page

  • If no wallet is connected (and demo mode is off), it shows a "Connect your wallet" card instead.
  • A greeting with the signed-in name, plus "New Campaign" and "Browse" buttons.
  • Four small tiles: Created, Contributions, Active Campaigns and the connected wallet address.
  • Recent Transactions: your last six donations, newest first, with the amount and the date.
  • Your Campaigns: one row per campaign you created, with a progress bar and a countdown for live ones.
  • Milestone Progress: for each of your campaigns, each milestone shown as Locked, Pending or Released.
  • Platform Statistics: total campaigns, total raised, contributions, backers, successful campaigns and treasury.
  • Saved Campaigns from your bookmarks, and a bell icon with notifications.

Where the data comes from

  • Your campaigns and donations come from the contract, filtered by your wallet address.
  • The transaction list is built from the donation records of the campaigns you gave to.
  • The numbers in the tiles are simply the sizes of those lists.
  • In demo mode the same page renders with fixed sample values, so it can be shown without a wallet or a network.
  • Progress bars and countdowns are calculated in the browser from the amounts and deadlines read on-chain.

/create-campaign — start a campaign

What is on the page

  • Same wallet guard: connect first, or it shows the "Connect your wallet" card.
  • Fields: title, description, category (10 choices), duration in days, target amount in ETH, campaign image, and an optional additional-information box.
  • While you type the target, it shows the same amount in USD / INR.
  • A preview of the fixed release plan: milestone 1 = 30%, milestone 2 = 30%, milestone 3 = 40%, with the ETH value of each one.
  • A short note that launching is free, and a "Create Campaign" button.

What happens when you press the button

  • The image is uploaded to IPFS through the server route, which returns a file address.
  • A JSON file with the title, description and category is uploaded to IPFS as well.
  • The contract is called with that metadata address, the target and the duration. No ETH is sent — creating a campaign is free and only costs gas.
  • The page waits for the transaction to be confirmed, shows a success message and opens the new campaign page.
  • If the wallet is on the wrong network, a warning tells you to switch before creating.
Why creating is free

There is no deposit and no listing fee, so a creator pays only gas. Trust comes from the escrow instead: the creator is paid step by step, and only when the donors approve the proof. The trade-off is that creating a campaign is cheap, so spam control now depends on the donor vote rather than on a deposit.

9Likely questions and answers

Click a question to open the answer.

"Is the data stored on the blockchain or in a database?"

Everything about money is on-chain inside the contract: campaigns, donations, milestones, votes, released amounts and status. There is no database at all. Only big files — images, metadata, proof files — are kept off-chain on IPFS, and the contract stores just their short file address. The few "database-like" things such as bookmarks, the demo flag and the theme live in the browser's own storage and are not part of the app's data.

"What stops a creator from taking the money and disappearing?"

Two things. First, nothing is released before the deadline, and only if the target was reached. Second, even then the creator cannot take the money themselves: they must post proof, and the donors who paid into the campaign must approve it, milestone by milestone, with a majority and 50% of the power taking part. On a campaign that missed its target, no release is possible at all and every donor can refund in full. The realistic worst case is a creator faking convincing proof for a funded campaign — the chain records what was claimed and how people voted, but it cannot check whether a photo is true.

"Why 30 / 30 / 40 and not three equal parts?"

The last part is the biggest, so the creator's largest payment depends on really finishing the project. It also soaks up the rounding left over from whole-number maths: Solidity has no decimals, so 40% worked out directly could leave a few tiny units stuck. The third milestone is calculated as whatever is left, so the three payments always add up to exactly 100% of the money held.

"What if the donors never vote — is the money stuck forever?"

Yes, and that is a real limitation of this version: a funded campaign whose milestones are never approved keeps its money locked with no end date. Only a campaign that misses its target has a way out, where every donor can refund. The fix would be a timeout or an arbitration path, which is listed in the roadmap.

"Who pays the gas fees?"

Whoever signs the transaction. A donor pays gas when donating and when voting; the creator pays gas when creating the campaign and when posting proof; and the person who presses Release pays for that transaction. Since anyone may press Release, the app could even pay for it later.

"How exactly is voting power calculated?"

Voting power is simply the amount of ETH that wallet has put into that campaign. There is no token and no separate voting coin. To approve, more than half of the votes cast must say yes, and at least 50% of the campaign's total power must take part. That total is fixed when the proof for the milestone is posted. If a donation is refunded it goes back to zero and the power with it.

"Does the login do anything for security?"

Not for the money. Clerk is an optional convenience that gives a display name and a picture; there is no server middleware guarding any page. The real security is the wallet signature and the contract rules — anyone can open the pages, but nothing that moves money can happen without a signed transaction from the right account. Clerk here is best described as credit, not as permission.

"How does the website know it matches the contract?"

The contract's interface file is generated from the compiled build by npm run export-abi, which rewrites constants/abi.js with a note at the top saying it is auto-generated. The deployed address is written into constants/index.js, and if an old NEXT_PUBLIC_CONTRACT_ADDRESS disagrees, it is ignored with a console warning so the app cannot quietly point at an old deployment.

"How was it tested? Was the deployed contract verified?"

There are 35 contract tests covering campaign creation, the escrow, proof, voting, refunds and the admin rules. One of them runs a full campaign and checks the exact payouts (3 / 3 / 4 ETH) and that the contract balance is zero at the end. Hardhat is set up for both Etherscan and Sourcify, so the deployed code can be checked against its source on-chain.

"What happens if the contract is paused or a campaign is switched off?"

Pausing blocks every function that moves money — create, donate, proof, vote, release. It is the emergency brake. Switching a campaign off removes it from the browse list. One side effect to flag: the refund function also checks that the campaign is active, so switching off a failed campaign also blocks refunds. That is an inconsistency worth fixing by relaxing that check.

"Could the platform owner take the escrow?"

Not through the normal path: the fee withdrawal is capped by the fees collected, which is zero in this setup. But the emergency withdrawal sends the whole contract balance to the owner, and that balance includes locked donor money. It is meant for disaster recovery, but it does mean the owner is trusted in that one case. The first change to make would be a time lock or a multi-signature rule on that function.

"What would be added next?"

An indexer (for example a subgraph) so the pages read totals instead of looping over every campaign; a small database for linking wallets to accounts; a second IPFS provider so files are safer; and gasless voting so a user with no ETH for gas can still vote.

10Glossary — the words used in this report

WordSimple meaning
WalletThe app that keeps your private key (here MetaMask). Whoever has the key controls the money.
DAppA website whose rules run in a smart contract instead of on a normal server.
Smart contractA program on the blockchain. Its code and data are public and it runs exactly as written.
EscrowMoney held by a neutral party until conditions are met. Here the neutral party is the contract itself.
MilestoneA checkpoint that must be finished and approved before the next part of the money is paid.
QuorumThe smallest share of voting power that must take part for a vote to count (50% here).
wei / ETHwei is the tiniest unit of Ether (10⁻¹⁸ ETH). The contract counts in wei; the page shows ETH.
GasThe fee paid to the network for running a transaction. The sender pays it.
ABIThe file that tells the website how to call each contract function and read its answer.
IPFS / CIDFile storage where the address is a hash of the file itself, so the address changes if the file changes.
PinningAsking a service (Pinata) to keep an IPFS file available for a long time.
RPC endpointThe web address a browser uses to read from and write to the blockchain.
TestnetA practice blockchain with coins that have no value — here Sepolia (chain ID 11155111).
Event / logA public note a contract writes down. It is how the full history can be read on a block explorer.
